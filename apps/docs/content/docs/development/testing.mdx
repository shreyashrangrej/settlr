Settlr has two kinds of automated tests. Every new feature gets some of
each, and both run before anything is pushed.

| Command (from the repo root) | Runs | Takes |
| --- | --- | --- |
| `pnpm test` | Backend tests (Vitest + `convex-test`) and the Android app's unit tests (Vitest) | A few seconds |
| `pnpm test:e2e` | Browser tests (Playwright) of the web app, then of the Android app | A few minutes from cold, seconds against a running test server |

## Backend tests

`packages/backend/convex/*.test.ts`. [`convex-test`](https://docs.convex.dev/testing/convex-test)
runs the real queries and mutations against an in-memory Convex in the
edge runtime, so there's no deployment, no browser and no sign-in. This is
where most tests belong: balances, splits, settling up, the trash, and who
can see or change what.

```ts
import { api } from './_generated/api'
import { as, setup, today } from './test.setup'

test('someone outside the group can’t see it', async () => {
  const t = setup()
  const groupId = await as(t, 'Alice').mutation(api.groups.create, {
    name: 'Goa trip',
    currency: 'INR',
    members: ['Bob'],
  })
  expect(await as(t, 'Mallory').query(api.groups.get, { groupId })).toBeNull()
})
```

`test.setup.ts` has the helpers: `setup()` makes a fresh backend, and
`as(t, 'Alice')` signs in a test user (it sets the identity's
`tokenIdentifier`, name and email, which is what `requireUser` reads).
Test a feature's rules as well as its happy path: the wrong user is
refused, bad values throw, and totals stay right after edits and deletes.

The Convex CLI skips files with more than one dot in their name, so test
files are never deployed. `pnpm --filter @settlr/backend test:watch` reruns
them as you save.

## Browser tests

`apps/web/e2e/*.spec.ts`. Playwright drives a headless Chrome through the
real app: the sign-in form, dialogs and live updates. Keep these to a
feature's main flow; the detailed cases go in the backend tests.

They never touch the dev deployment. `apps/web/e2e/server.mjs`, which
Playwright starts for you:

1. downloads the open-source Convex backend once (a pinned version, into
   `apps/web/e2e/.state`),
2. starts it on ports 3310/3311 with an empty database, sets `SITE_URL`,
   `BETTER_AUTH_SECRET` and `TRUSTED_ORIGINS`, and deploys
   `packages/backend/convex` to it,
3. builds the web app against it into `.next-e2e` (so `pnpm dev` and
   `pnpm build` are left alone) and serves it on http://localhost:3100.

There's no `RESEND_API_KEY` there, so sign-in codes stay in Better Auth's
`verification` table, and `e2e/admin.ts` reads them. The helpers in
`e2e/fixtures.ts`:

| Helper | Does |
| --- | --- |
| `test` with `user` | Gives the test a page signed in as a new account |
| `otherUser(browser, 'Bob')` | A second account in its own browser context |
| `signIn(page, email)` | Signs in through the login form, filling in the name step for new accounts |
| `createGroup(page, name, members)` | Creates a group through the form |
| `addExpense(page, amount, description)` | Adds an expense from an expense page's "Add expense" button |

```ts
import { addExpense, createGroup, expect, test } from './fixtures'

test('split an expense', async ({ user: { page } }) => {
  await createGroup(page, 'Goa trip', ['Bob', 'Cara'])
  await addExpense(page, '90', 'Dinner')
  await expect(
    page.getByRole('main').getByRole('region', { name: 'Your balance' }),
  ).toContainText('+$60.00')
})
```

Every account is new (`uniqueEmail`), so tests can run in parallel and
against a server that's already up. Find elements the way people do, by
role and label (`getByRole`, `getByLabel`), and scope them to
`getByRole('main')` or the `dialog`, since the top bar repeats some
buttons ("Add expense" is also the "New" menu).

### Running them faster

The cold start is mostly the production build. While you write tests,
start the test server once and leave it running; `pnpm test:e2e` reuses it:

```bash
pnpm --filter web e2e:server             # production build
E2E_DEV=1 pnpm --filter web e2e:server   # next dev: starts at once, compiles pages on first visit
```

Restart it after changing `convex/` (it deploys once, at start) and, for a
production build, after changing the app.

### When one fails

Playwright saves a screenshot, the page's accessibility tree
(`error-context.md`) and a trace under `apps/web/test-results/`. Open the
trace with `pnpm --filter web exec playwright show-trace <path>/trace.zip`.
The backend's own log is `apps/web/e2e/.state/backend.log`.

## The Android app

The Android app (`apps/mobile`) has two kinds of tests of its own.

**Unit tests**, `apps/mobile/src/lib/*.test.ts` (Vitest), cover the plain
logic the screens use: Home's sums of balances, Add expense's splits and the
arguments it sends to Convex, the amount keypad, money and date formatting,
the guessed category and the saved settings.

**Browser tests**, `apps/mobile/e2e/*.spec.ts` (Playwright), run the app's
own screens, built for the web with `react-native-web`, in Chromium at a
Pixel 7's size. `apps/mobile/e2e/server.mjs`, which Playwright starts:

1. starts the same throwaway Convex backend as the web tests
   (`apps/web/e2e/server.mjs` with `E2E_BACKEND_ONLY=1`), or reuses one
   that's running,
2. exports the app for the web into `apps/mobile/dist-e2e`, pointed at it,
3. serves it on http://localhost:3200 and forwards `/api/auth/*` to the
   backend the way the web app's auth route does, so sign-in cookies are
   first-party.

The helpers in `apps/mobile/e2e/fixtures.ts`: `test` with `user` (a new
signed-in account, through Welcome and the code), `createGroup`,
`fillExpense` and `typeAmount` (the keypad), `slide` (Slide to record), and
`seen(page, text)` / `button(page, name)`. Use those two rather than plain
`getByText`: on the web, the screens behind the one in front stay in the
page (pushed ones hidden, other tabs `inert`), and they only match what's
in front.

Turbo runs the Android browser tests after the web ones, since both use the
same ports. While writing them, keep a server running with
`pnpm --filter mobile e2e:server` (restart it after changing the app, which
it builds once).

## CI

`.github/workflows/test.yml` runs the type check, the unit and browser tests of both apps and the
docs build on every push to `main` and on pull requests (the browser tests
include a production build of the web app), and uploads the Playwright
reports, screenshots and traces (of both apps) when a browser test fails.
