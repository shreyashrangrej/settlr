# CLAUDE.md

Settlr is an expense-splitting app built on Next.js 16 (App Router, React
19, Turbopack) with Convex as the backend and Better Auth for sign-in. It's
a Turborepo monorepo (pnpm workspaces): `apps/web` (the app, package
`web`), `apps/mobile` (the Android app, package `mobile`), `apps/docs` (the Fumadocs documentation site, package `docs`),
`packages/backend` (`@settlr/backend`, the `convex/` folder) and
`packages/shared` (`@settlr/shared`, code both sides use). See `README.md`
for the feature overview, and the docs (`apps/docs/content/docs`, live at
https://settlr-docs.vercel.app) for the details, including the per-route
rendering table in `development/web-app.mdx`.

## Commands

Use **pnpm** only (no npm/yarn lockfiles). Run these from the repo root;
Turborepo runs each in the workspaces that define it.

```bash
pnpm install
pnpm dev              # the web app, http://localhost:3000
pnpm dev:docs         # the docs, http://localhost:3001
pnpm dev:mobile       # the Android app in Expo Go (scan the QR code)
pnpm dev:convex       # push packages/backend/convex to the dev deployment on every change (run alongside dev)
pnpm typecheck        # every workspace (web/docs: next typegen && tsc --noEmit)
pnpm build            # builds apps/web and apps/docs
pnpm start            # run the web app's production build
```

One workspace: `pnpm --filter web build`, `pnpm --filter docs dev`. Run
the Convex CLI (`pnpm exec convex ...`) from `packages/backend`, where its
`.env.local` (`CONVEX_DEPLOYMENT`) is.

There is no test suite or linter yet. Before committing, run
`pnpm typecheck && pnpm build`. The build is also what enforces the
server/client boundaries (`server-only` imports, client functions called
from server components). When a change alters what the app does or how it's
built, update the matching page in `apps/docs/content/docs` too.

## Git workflow

Always push finished work to `main` on GitHub, unless the user says
otherwise for a given change. If you work on a feature branch, push it and
then fast-forward `main` to it (`git push origin HEAD:main`). Never
force-push `main`.

## Layout

Paths under `src/` below are in `apps/web`; `convex/` is
`packages/backend/convex`.

- `convex/`: the Convex backend, where all app data lives. `schema.ts`
  (friends, friendEntries, groups, groupExpenses, groupPayments,
  personalExpenses, receipts, budgets, notifications), `friends.ts`, `groups.ts`,
  `personal.ts`, `budgets.ts`, `notifications.ts`, `receipts.ts` (queries
  and mutations), `expenses.ts` (`month`: every expense you're part of in
  a month, across groups, friends and personal, for `/expenses` and the
  dashboard's recent list), `assistant.ts` (the `/assistant` chat: an action that
  calls OpenRouter with tool calling, plus the internal queries its search
  and edit tools read through; the tools, in `lib/assistantTools.ts`, add, find
  and edit expenses and create groups and friends; they write through the
  public mutations above as the caller (creating reloads the friends and
  groups the tools match names against, so one reply can create a group
  and add to it), and deleting is only offered, the user confirms it in
  the chat), `mcp.ts` (the same tools
  over MCP for Claude/ChatGPT: `handle` answers one JSON-RPC request as the
  caller, deleting is a real tool marked destructive; plus the connected
  apps for Settings), and `lib/` (`requireUser`, value checks in `input.ts`,
  balance math in `ledger.ts`, receipt attach/delete in `receipts.ts`, enum
  validators). `auth.ts` is the Better Auth instance
  (email OTP + Google, `@better-auth/expo` for the Android app with
  `settlr://` always trusted, plus Better Auth's `mcp` OAuth plugin and the
  `mcpBridge` plugin: it forces a consent step on every MCP authorization,
  rotates refresh tokens, and swaps an MCP access token for a Convex JWT at
  `/api/auth/mcp/convex-token`), `http.ts` mounts its routes, `convex.config.ts`
  mounts the `betterAuth` component and declares the typed deployment env
  vars. `convex/_generated/` is generated by `convex dev`; commit it.
  Import it from the web app as `@settlr/backend/convex/_generated/api`
  (and `.../dataModel` for types). `convex/` must not import from
  `apps/web`; code both sides need goes in `packages/shared`.
- `packages/shared/src/`: `@settlr/shared`, TypeScript source used by the
  web app and Convex. `schemas.ts` (`@settlr/shared/schemas`: currencies,
  categories and the zod schemas shared by search params and forms, with
  the limits `convex/lib/input.ts` also checks) and `format.ts`
  (`@settlr/shared/format`: money and date formatting). The web app
  compiles it through `transpilePackages`; add new files to its `exports`.
- `apps/docs/`: the documentation site (Fumadocs on Next.js). Pages are
  MDX in `content/docs` (`guide/` for people using the app,
  `development/` for people working on it), ordered by each folder's
  `meta.json`; MDX components are registered in `components/mdx.tsx`.

- `apps/mobile/`: the Android app, Expo (SDK 58) with Expo Router,
  built in phases (the plan is in Notion). `src/app/` routes (`(tabs)/`
  holds Home, Groups, Friends, Personal, Assistant), `src/theme/` the
  `DESIGN.md` tokens for dark and light (`useColors()` follows the phone),
  `src/components/` (`Text` picks the DM Sans family per weight, since
  Android ignores `fontWeight` for custom fonts; `Button`, `TabBar`,
  `Screen`, `icons` (Lucide via `lucide-react-native`)), `src/lib/convex.ts` and `src/lib/auth-client.ts`
  (Better Auth's `expoClient`, session in `expo-secure-store`). Sign-in
  is `sign-in.tsx` and `verify.tsx`; the root layout guards routes with
  `Stack.Protected` on the session, so signing in or out needs no
  navigation. Imports use `@/` for its `src/`. It
  must keep running in Expo Go, so add packages with `npx expo install`
  and only use native modules Expo Go ships. `.env.local` has
  `EXPO_PUBLIC_CONVEX_URL`, `EXPO_PUBLIC_CONVEX_SITE_URL` and
  `EXPO_PUBLIC_SITE_URL` (auth goes through the web app's origin, since
  Google returns there). Check with
  `pnpm --filter mobile typecheck` and `pnpm --filter mobile
  export:android`; `pnpm build` doesn't build it, and release APKs are
  built on GitHub Actions (no EAS). The Android mockups in
  `design/screens/android/` are its reference. Docs:
  `development/mobile-app.mdx`.
- `design/`: the design handoff the UI follows. `DESIGN.md` has the tokens
  and component notes; `screens/*.html` are static mockups (web dashboard,
  add-expense, assistant, and three mobile screens). Their data is sample
  data: things in them the backend doesn't have (UPI, reminders, upcoming
  bills, group budgets, exact/percent splits, saved chats, undo) aren't built.
- `src/app/`: the App Router. `layout.tsx` is the root document (reads the
  auth session, renders `<Providers>` and the `<AppShell>`), `page.tsx` the
  landing hero. `(app)/` is the signed-in area: its layout redirects to `/`
  when signed out, and the dashboard, all expenses (`expenses/`), friends,
  groups, personal, budget, notifications and receipt viewer pages live
  under it. Each page is a
  server `page.tsx` that prefetches data and renders a client `view.tsx`
  beside it; `loading.tsx` is its skeleton. Route groups `(list)`,
  `(detail)` and `(expenses)` only exist to give sibling pages their own
  `loading.tsx` (a folder's `loading.tsx` also covers everything nested in
  it). `api/auth/[...all]` proxies Better Auth to Convex; `api/health` is a
  liveness probe. `api/mcp` is the MCP server (stateless Streamable HTTP:
  swaps the bearer token for a Convex JWT, then calls `api.mcp.handle`),
  `.well-known/oauth-*` serve Better Auth's OAuth metadata from the site
  root, and `connect/` is where MCP clients send people to sign in
  (`LoginForm` with `next`) and approve the app.
- `src/server/`: server-only code (every file imports `server-only`).
  `auth.server.ts` (Better Auth's Next.js adapter: `handler`, `getToken`,
  `fetchAuthQuery`, and the per-request `getAuthSession()`) and
  `convex.server.ts` (`prefetchQuery`) and `mcp.server.ts` (MCP token
  exchange, OAuth metadata proxy).
- `src/lib/`: isomorphic code: `types.ts`, `dashboard.ts` (the recent

  `search.ts` (`parseSearch`, `searchHref`), `preferences.ts`

## Conventions

- **Server vs client components**: files under `src/app` are server
  components unless they start with `'use client'`; `view.tsx`, most of
  `src/components` and the Base UI parts of `components/ui` are client
  components. A server component may render client components but can't
  call functions exported from a `'use client'` module (e.g.
  `buttonVariants()`: it fails at request time), so keep server components
  to data loading and composition. Server-only code lives in `src/server/`
  and imports `server-only`.
- **Data** goes through Convex, not server actions. A server `page.tsx`
  (or layout) prefetches with `await prefetchQuery(api.x.y, args)` and
  wraps its view in `<Prefetched queries={[result.entry]}>`; the view reads
  with `useSuspenseQuery(convexQuery(api.x.y, args))`, which in the browser
  becomes a live subscription, so don't call `router.refresh()` after
  mutations (`useConvexMutation`). Pass the args in the same key order on
  both sides: Convex hashes query keys with `JSON.stringify`. Queries that
  take an id from the URL accept a string, `normalizeId` it and return
  `null` for missing or foreign rows; the page turns that into
  `notFound()`. Dynamic titles use `generateMetadata`, which can call
  `prefetchQuery` too (it's cached per request).
- **Session**: `getAuthSession()` on the server (cached per request),
  `useSession()` in client components. Layouts don't re-render on client
  navigation, so anything that changes who is signed in or their profile
  must call `router.refresh()` (sign-in pushes to `/dashboard` then
  refreshes; sign-out does a full page load to `/` so nothing of the
  account stays in memory).
- **Navigation**: `next/link` with string hrefs, `<NavLink>` for links that
  show the current page, `useAppRouter()` (from `navigation-progress.tsx`)
  instead of `useRouter()` for programmatic navigation so the progress bar
  shows. `useParams()` works in client components; pages pass params and
  parsed search params down as props.
- **Search params** are parsed on the server with
  `parseSearch(zodSchema, await searchParams)`; the schemas use
  `.default(x).catch(x)` on every field (and `z.coerce` for numbers), so bad
  URLs fall back instead of throwing. Build URLs with `searchHref(pathname,
  values, defaults)`, which leaves defaults out.
- **Money** is stored as integer minor units (`amountCents`), never floats.
  All currencies in `CURRENCIES` have 2 decimals.
- **Hydration safety**: SSR-rendered routes format with the fixed `en-US`
  locale and UTC (`@settlr/shared/format`). Anything that depends on the viewer's
  locale, time zone, clock or browser storage goes inside `<ClientOnly>`
  (the page can still prefetch its data) or in a `useEffect`. Values like
  "this month" and "today" are computed in the server page and passed down. For the viewer's locale use
  `new Intl.NumberFormat().resolvedOptions().locale`, not
  `navigator.language`, which can be an invalid tag such as `en-US@posix`.
- **Design**: the web app follows Gr8r Studio's design system
  (github.com/gr8rstudio/gr8r-studio, see `design/DESIGN.md`): warm paper
  neutrals in light and warm charcoal in dark (it follows the system
  until the viewer picks one), an indigo `primary`, Geist and Geist Mono,
  Lucide icons at a 1.8 stroke. Money is green (`positive`, owed to you)
  or red (`destructive`, you owe), always with a word or a sign beside it,
  in the UI font with `tabular-nums` (no monospace), via `SignedAmount`
  where it has a direction. Semibold only for headings and big figures;
  `font-medium` for buttons, labels, row titles and badges; descriptions
  `text-xs text-muted-foreground`. Cards are `rounded-xl border bg-card`
  (10px, no shadow) with `p-3.5`, titles `text-sm font-semibold`; inner
  tiles and controls `rounded-lg` (6px), badges `rounded-md` (5px);
  menus, selects and popovers use `popover-panel`, dialogs `modal-panel`.
  Controls are `h-7.5` (30px) from `sm` (`h-8.5` below): don't override
  their heights. Sidebar section labels are Gr8r's uppercase `text-2xs`
  headings. `Tabs` is the segmented control (`variant="line"` for
  underlined tabs); `Button`'s `outline` is Gr8r's secondary button, it
  has a `contrast` variant (the "Settle" button) and `destructive` is a
  solid red confirm.
- **Styling**: use shadcn components and Tailwind utilities (no new
  hand-written CSS). Base UI uses a `render` prop, not `asChild`: e.g.
  `<Item render={<Link href="..." />}>` or `<DropdownMenuTrigger
  render={<Button />}>`. For a link that looks like a button, put
  `buttonVariants(...)` on a `<Link>`. Confirm destructive actions with
  `ConfirmAction`, not `window.confirm`, and report success with
  `useAction(fn, { success: '...' })` (a sonner toast).
- **Layout**: pages are centred at up to 1160px beside the sidebar
  (padding `px-4 sm:px-6`, Gr8r's gutter, set by `AppShell`), with 16px
  (`gap-4`) between cards and 20px under the page header. Rows of cards are `flex flex-wrap` with
  `flex-[grow_1_basis]` so they stack on narrow screens. The dashboard is
  two independent columns from `xl` (so no card stretches to match a
  neighbour); below that the column wrappers are `contents` and
  `max-xl:order-*` sets the single-column order.
  Summary figures go in a `StatGrid` of `StatCard`s
  (`src/components/stat-card.tsx`), lists of records are tables whose extra
  columns appear on wider screens (`hidden md:table-cell`, with the details
  folded into the first cell below that); expense lists get this from
  `ExpenseTable`/`ExpenseRow`, so build new ones on those. Expense pages
  (a group, a friend, personal, all expenses) share one shape: `PageHeader`
  with a `PageIcon` or avatar, outline secondary buttons and a primary "Add
  expense", then `ExpensePage` (stats strip, then the list beside the side
  cards, whose top lines up with the list's card, not its filter toolbar:
  `SplitLayout` offsets the aside when the content has the
  `data-slot="expense-toolbar"` bar). Their forms open from header buttons
  in a dialog (`ExpenseDialog` for expenses, `FormDialog` for the rest), not side cards, and other views of the same thing (a
  group's Insights) are header buttons too, not tab rows. Every
  `ExpenseTable` has the same columns at the same widths: Description,
  Date, two middle columns (`columns={['Paid by', 'Split']}`, or
  `['Where', 'Paid by']` across sources), Amount and the "⋯" menu. Tables follow
  Gr8r's members table: they run edge to edge inside their card (no padded
  `CardContent` around them; `ui/table.tsx` puts the first and last
  columns on the card's 14px gutter), any filter bar sits above the card
  (`ExpenseSection` does both), and row actions are one "⋯" menu
  (`RowActions`). Tables are `table-fixed`: the short columns get fixed
  widths (`w-28` date, `w-32 sm:w-40` amount, so "Your share" fits under it, `w-12` actions) and the first column
  takes the rest, with an icon tile (e.g. `CategoryIcon`) or avatar and a
  faint second line (see the group, personal and budget tables). Rows
  have no hover fill. Collections of things (friends,
  groups) are card grids with `repeat(auto-fill,minmax(…,1fr))`, and forms
  get a max width. `SplitLayout` gives a page a main area and a 22rem
  sidebar from 1400px (below that the column beside the app sidebar is too
  narrow, so it stacks). Viewport breakpoints see the whole window, not the
  content column, which is about 260px narrower on `lg` and up (the 252px
  sidebar and the rim; about 60px with the sidebar collapsed) and at most
  1160px wide.
- **Loading**: give each page a `loading.tsx` rendering its page-shaped
  skeleton from `src/components/skeletons.tsx`. The top bar
  (`navigation-progress.tsx`) starts on link clicks and `useAppRouter()`
  navigations. Nested pages pass `back={{ fallback: '/path', label }}` to
  `PageHeader` for a back button (phones only; wider screens use the top
  bar's breadcrumb, which `app-shell.tsx` builds from the path).
- Dark mode is the `.dark` class on `<html>` (set before paint by the inline
  script in `src/app/layout.tsx`: the viewer's saved choice, otherwise the
  system setting), not `prefers-color-scheme`, so style dark variants
  with `.dark` / `dark:`. Theme-dependent markup must render the same on the
  server, e.g. render both icons and hide one with `dark:hidden`.
  Element-level CSS rules go in `@layer base`, or they override Tailwind
  utilities.
- Imports in `apps/web` use the `#/` alias for its `src/` (e.g.
  `#/lib/search`); shared code is `@settlr/shared/schemas` and
  `@settlr/shared/format`.

## Gotchas

- Convex deployment env vars (`pnpm exec convex env list`): `SITE_URL`
  (the app origin: on the dev deployment, the Vercel site),
  `TRUSTED_ORIGINS` (other origins allowed to sign in, comma-separated; the
  dev deployment has `http://localhost:3000,exp://`: email codes work on
  localhost but Google sign-in returns to `SITE_URL`, and `exp://` lets
  Expo Go sign in), `BETTER_AUTH_SECRET`, and optional
  `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` (Google sign-in is off until
  both are set) and `RESEND_API_KEY`/`AUTH_EMAIL_FROM`. Without a Resend
  key, sign-in codes are only logged: read them with
  `pnpm exec convex logs`. The assistant needs `OPENROUTER_API_KEY` and
  `OPENROUTER_MODEL` (an OpenRouter model slug that supports tool calling);
  without them `/assistant` says it isn't set up. Set values with the
  `NAME=value` form.
- MCP OAuth: the issuer is `SITE_URL`, so test MCP clients against that
  origin. The token exchange calls the Convex plugin's `getToken` endpoint
  with a stand-in session (`mcpBridge` in `convex/auth.ts`), which leans on
  Better Auth internals; recheck it when upgrading `better-auth`.
- `better-auth` (and `@better-auth/expo`) is pinned to the exact version
  `@convex-dev/better-auth` is built against (1.6.15). Newer 1.6.x releases break the
  `ConvexBetterAuthProvider` types. Upgrade the two together.
- To call Convex functions from the CLI as a test user, run the CLI with
  node from `packages/backend`, not `pnpm exec` (cmd.exe mangles the JSON
  on Windows): `node node_modules/convex/bin/main.js run --identity '{"tokenIdentifier":"test|u1","name":"Test"}' friends:list '{}'`.
- To sign in locally without a real inbox, request a code for
  `delivered@resend.dev` (Resend's test address) and read it with
  `pnpm exec convex data --component betterAuth verification`.
- `apps/web/.env.local` needs `NEXT_PUBLIC_CONVEX_URL` and
  `NEXT_PUBLIC_CONVEX_SITE_URL` (the `.convex.site` URL);
  `packages/backend/.env.local` has `CONVEX_DEPLOYMENT` for the CLI.
  `convex dev` there doesn't write the web app's file, so copy the URLs. `NEXT_PUBLIC_*`
  values are inlined at build time, so rebuild after changing them.
- Pages with a `loading.tsx` stream: the status is sent before the page
  finishes, so a `notFound()` there still responds 200 (with the not-found
  UI and a `noindex` tag).
- Deployment: the Vercel project `settlr` is the dev environment, with
  Root Directory `apps/web`. It's connected to GitHub and deploys every
  push to `main` (other branches are off in `apps/web/vercel.json`). Its
  build (`buildCommand` in `apps/web/vercel.json`) runs `convex deploy` in
  `packages/backend` with `CONVEX_DEPLOY_KEY`, a deploy key for the dev
  Convex deployment, so `convex/` is pushed to it before `next build` runs
  in `apps/web`; a push to `main` updates both. That overwrites whatever
  `pnpm dev:convex` pushed from a local checkout. The docs deploy as the
  separate Vercel project `settlr-docs` (Root Directory `apps/docs`,
  https://settlr-docs.vercel.app), also on every push to `main`. The web
  app links to them through `DOCS_URL` in `src/lib/site.ts`
  (`NEXT_PUBLIC_DOCS_URL` overrides it).
  `transpilePackages` in `apps/web/next.config.ts` compiles
  `@convex-dev/better-auth` and `@settlr/shared`.
- `ui.shadcn.com` may be blocked in sandboxed environments. The registry
  sources are on GitHub (`apps/v4/registry/bases/base/ui/*.tsx`, with the
  nova style's `cn-*` classes in `apps/v4/registry/styles/style-nova.css`);
  `calendar.tsx` and `popover.tsx` were added from there by hand.
- `components.json` has `"rsc": true`, so `shadcn add` puts `'use client'`
  on components that need it; check hand-copied ones do too.
- Run `shadcn add` in `apps/web`. It writes `import { cn } from "cn"` and installs an unrelated npm
  package named `cn`. After adding components, change the import to
  `#/lib/utils` and run `pnpm remove cn`. It may also add `next-themes`
  (for sonner); this app's toaster follows the `.dark` class instead, so
  remove it. Don't re-run `shadcn init`: it would overwrite the theme in
  `styles.css`. The `data-horizontal`/`data-vertical` variants that init
  would add are defined there by hand.
- Add packages to the workspace that uses them (`pnpm --filter web add
  <pkg>`), not the root. After adding packages while `pnpm dev` is
  running, restart it.
